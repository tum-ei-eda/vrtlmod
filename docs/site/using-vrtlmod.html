User guide

Use vRTLmod in your simulation

Choose the generated state you want to instrument, build its injection API into your harness, and control when faults enter the model.

The workflow

  1. Generate a C++ or SystemC model with Verilator.
  2. Run vRTLmod on the generated sources and headers.
  3. Inspect the target inventory and optionally select a subset with a whitelist.
  4. Compile the rewritten model, generated API, and required Verilator runtime into your simulation.
  5. Prepare and arm a target, then drive the model's clock or event from your harness.

vRTLmod instruments generated C++; it does not replace Verilator or run a fault campaign by itself. Start with the complete counter example if you have not yet built an instrumented simulation.

Keep the toolchain consistent

Build vRTLmod against the same Verilator installation used to generate its input model. The supported major versions are 4 and 5, with v5 compatibility targeting 5.054. LLVM/Clang versions 13–18 are supported.

When configuring this repository or its maintained CMake examples, Verilator selection follows this order:

  1. VERILATOR_ROOT passed to CMake, including a cached value.
  2. The VERILATOR_ROOT environment variable.
  3. verilator on PATH.

An explicit root can name a source/build tree, an installation prefix, or its share/verilator directory. Invalid explicit roots fail configuration. CMake reports the selected executable, runtime root, and version, then uses matching headers and the matching Verilator CMake package.

cmake -S . -B build-custom \
  -DVERILATOR_ROOT=/path/to/verilator-install \
  -DLLVM_DIR=/path/to/llvm/lib/cmake/llvm \
  -DCMAKE_CXX_STANDARD=17

The selected root is cached. Use separate build directories for different installations. A CMake selection does not change the verilator command in your shell: use that same installation's command when generating model inputs manually.

C++17 is the default and needs no Boost dependency. Builds with older C++ standards use Boost.Filesystem; LLVM 16–18 require at least C++17. SystemC models additionally need a compatible SystemC installation built with a matching C++ standard.

Run the command line tool

Provide the generated model's C++ files and headers. Keep Verilator's own runtime sources separate: they belong in the simulation build, not in the instrumentation input set.

vrtlmod --out=modified obj_dir/Vcounter*.cpp obj_dir/Vcounter*.h \
  -- /usr/lib/llvm-18/bin/clang++ -xc++ -std=c++17 -Iobj_dir

The example uses the prefix Vcounter and LLVM 18; adapt both to your model and toolchain. vRTLmod adds include paths from its build configuration automatically. Supply additional model or library includes after --. Use --no-auto-include only when you intend to provide all required include paths yourself.

Input basenames are copied into the output directory, so use separate output directories for models with colliding filenames. Do not pass build scripts, makefiles, or unrelated source trees as model inputs.

OptionPurpose
--out=DIRWrite copied and rewritten code to DIR. Default: vrtlmod-out.
--systemcInterpret the input as a Verilator SystemC model. Also provide SystemC's include directory to Clang.
--xml-onlyAnalyze the model and write its XML inventory without generating the injection API. Use a separate analysis output directory.
--wl-regxml=FILESelect injectable variables using an edited vRTLmod XML inventory.
--overwriteModify the supplied source and header files in place. Omit this for the normal copy-to-output workflow.
--verbose, -vInclude detailed diagnostic output.
--silent, -sSuppress warning and informational logging.
--no-auto-includeDisable automatically added Verilator, Clang, and standard-library include paths.
--diff-unrollUnroll multidimensional accesses in generated differential comparison code.
--print-tdPrint the common target-dictionary header.
--helpShow available command-line options, including Clang tooling options.

The --overwrite option controls whether input files are modified. Existing files in a normal output directory can still be replaced when you rerun the command.

Choose injection targets

The generated Vcounter-vrtlmod.xml describes analyzed modules and variables. Variables with injection locations are eligible for instrumentation. This is vRTLmod's analysis XML, distinct from Verilator's own netlist XML.

For a two-pass selection workflow, first analyze the original generated model:

vrtlmod --xml-only --out=inventory \
  obj_dir/Vcounter*.cpp obj_dir/Vcounter*.h \
  -- /usr/lib/llvm-18/bin/clang++ -xc++ -std=c++17 -Iobj_dir
cp inventory/Vcounter-vrtlmod.xml whitelist.xml

Edit whitelist.xml by deleting unwanted variable nodes while retaining the surrounding module structure and attributes of retained entries. Then instrument the original generated inputs again:

vrtlmod --wl-regxml=whitelist.xml --out=selected \
  obj_dir/Vcounter*.cpp obj_dir/Vcounter*.h \
  -- /usr/lib/llvm-18/bin/clang++ -xc++ -std=c++17 -Iobj_dir

Check the selected dictionary before a campaign. A nonexistent whitelist path currently produces a warning and falls back to the unfiltered target set. The analysis XML is written before filtering; inspect the reported remaining targets and the generated API's td_ dictionary to confirm the selection.

Target inventory follows Verilator's generated clocked regions. Optimization can split arrays into separate targets, rename variables, or merge other assignments into those regions. Regenerate and review the whitelist when changing the RTL, Verilator version, or optimization settings.

Prepare, arm, clock, disarm

For a model with prefix Vcounter, include Vcounter_vrtlmodapi.hpp and construct VcounterVRTLmodAPI. Its vrtl_ member owns the instrumented Verilator model. Its public td_ dictionary maps generated target names to entries.

Inside your simulation harness, enumerate injectable entries before selecting a name:

VcounterVRTLmodAPI simulation;
for (const auto &entry : simulation.td_) {
    if (entry.second->injectable_)
        std::cout << entry.first << ": " << entry.second->bits_ << " bits\n";
}

The following is a harness fragment, not a complete program. Replace the target name with one from your generated dictionary and supply tick() to drive the relevant clock and call eval():

auto *target = simulation.get_target("TOP.count");
if (!target || !target->injectable_)
    return 1;

target->disarm();
target->reset_mask();
if (simulation.prep_inject(*target, 0) != vrtlfi::td::TD_API::GENERIC_OK)
    return 1;
target->arm();
tick();
target->disarm();

prep_inject() defaults to a bit flip, adds the selected bit to the mask, and resets injection counters. It does not arm the target. Clear the mask before a new independent selection, check the return code, and explicitly arm and disarm the entry.

Generated update hooks apply the fault during simulation. Arming an entry does not schedule a clock event; your harness remains responsible for clocks, reset, enables, and evaluation. Observe the result through ordinary model outputs or the entry's read_data(); use get_cntr() to inspect injection counts. The counter harness also checks the expected output independently.

For SystemC, generate the input with Verilator's SystemC mode and pass --systemc to vRTLmod. Bind the model's ports to SystemC signals, then advance simulation with sc_start(). The maintained SystemC harness shows that sequence.

Integrate with CMake

The installed cmake/vrtlmod-config.cmake package provides vrtlmod(), which adds the instrumentation command to your build. It does not create or link the final simulation target.

The maintained test/fiapp example demonstrates the complete SystemC integration. From a vRTLmod checkout with vRTLmod and SystemC already installed:

cmake -S test/fiapp -B build-fiapp \
  -DVRTLMOD_ROOT="$PWD/install" \
  -DSystemCLanguage_DIR=/path/to/systemc/lib/cmake/SystemCLanguage
cmake --build build-fiapp --parallel 2
./build-fiapp/fiapp-cmake-test build-fiapp/diff.csv

Adjust the install locations, and select the same Verilator used to build vRTLmod. This example uses SystemC; it is separate from the plain C++ counter walkthrough.

For your own build:

  1. Generate the original model and collect its model sources and headers.
  2. Load vRTLmod with find_package(vrtlmod CONFIG REQUIRED), using vrtlmod_DIR or CMAKE_PREFIX_PATH to locate the installed package.
  3. Call vrtlmod(SOURCES … OUTPUT … OUT_DIR … INCLUDE_DIRS …). Declare the rewritten model and generated API sources in OUTPUT.
  4. Compile those outputs into your target, include their directory, and link the runtime sources and libraries required by the selected Verilator model.

The helper accepts SYSTEMC, WHITELIST_XML, VERBOSE, and SILENT. Clang and SystemC include/tool paths can also be supplied explicitly; see the package implementation for the full argument list.

Reuse Verilator's selected runtime. The maintained example reads the original model target's SOURCES property and collects its verilated*.cpp files. It also links VERILATOR_MT_CFLAGS. This avoids missing runtime symbols when a Verilator version needs additional sources, such as verilated_threads.cpp.

The repository's FindVERILATOR.cmake adds vrtlmod_verilate(target …) for consistent toolchain selection during configuration and regeneration. It accepts upstream verilate() arguments and keeps the caller's environment intact. Older Verilator packages without a command hook require a Makefile or Ninja generator for this adapter. The adapter belongs to the repository's discovery module; the installed vrtlmod() package does not itself provide it.

Compare faulty and reference runs

vRTLmod also emits Vcounter_vrtlmod_diffapi.hpp and associated C++ sources. The generated VcounterVRTLmodAPIDifferential can compare two API-backed models, report target differences, and produce difference vectors or CSV output. See the C++ integration harness for compare_fast(), dictionary comparison, and CSV usage.

For validation, retain an unmodified model as well. Give it a distinct Verilator prefix if it shares an executable with the instrumented model, drive both with identical inputs, and compare observable behavior with injection disabled. The maintained tests use this independent baseline in addition to the generated differential API.

Coverage and practical limits

Regression coverage includes cycle-based C++ and SystemC models, the downstream CMake helper, scalar and multidimensional state, helper-call destinations, and clock/reset scheduling with split, inlined, and separate generated functions. The main compatibility baseline uses Verilator 4.228 and 5.054 with LLVM 18 and SystemC 2.3.4; 5.020 and 5.046 were also integration-tested during development.

Timing/coroutines, DPI, and multithreaded simulation are not covered by those integration tests. Generated storage shape and target names can change with optimization. Review the inventory and validate fault placement against your own model before using a new configuration for a campaign.

If parsing fails, first check the Verilator version match, model headers, C++ standard, and additional include paths. Add --verbose to collect diagnostics and consult the contributor guide for targeted regression commands.
